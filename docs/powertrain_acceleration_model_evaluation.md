# Powertrain and Acceleration assistant: evaluation and production recommendation

Evaluation date: 2026-10-05. This study covers the implemented **Powertrain Sizing** and **Acceleration** views, their shared vehicle/motor inputs, and the indexed local test documents. The [inspection snapshot](powertrain_acceleration_architecture.md) was written before optimization; the [58-entry capability map](../evaluation/capability_map.json) and [90-question dataset](../evaluation/questions.json) make the scope auditable.

## What the application actually provides

VMI is a Python CustomTkinter desktop application with Matplotlib plots. Analysis runs in-process through Python mixins. There is no application REST backend or DTO layer. The assistant sidebar captures selected UI fields, computed observations and a small plot snapshot. It routes a request to a checked local reply, a state read, document retrieval, or Ollama chat. Ollama is the only HTTP service in this path. The assistant has no tool access to edit inputs or press Plot.

The focused paths compute wheel torque and force from motor torque, reduction ratio, gear efficiency and wheel radius. Road load combines rolling, aerodynamic and grade forces. A theoretical motor envelope uses peak torque below base speed and a power-limited region above it; an uploaded torque-speed curve can replace it. Optional battery DC voltage/current limits cap shaft capability after efficiencies. The Powertrain report estimates top speed at a force crossing and a maximum startable grade. The Acceleration plot integrates available minus resistive force over effective inertial mass, including wheel inertia, and reports target time, final speed, crossing speed and settling time. The report and plot acceleration methods have different integration steps, so small differences are expected. Key input/output names, units, dependencies and code locations are in the capability map.

The assistant uses a 4,096-token context, temperature 0.2 and a default Qwen3 4B instruct model. RAG ingests PDF, DOCX, XLSX/XLS, TXT, Markdown, CSV and JSON from `knowledge_base/`, splits text into 300-word chunks with 50-word overlap, embeds with local `nomic-embed-text`, and stores cosine vectors in persistent Chroma. Query search uses source-name preference, vector candidates, a 0.33 distance cutoff and a lexical/section rerank, then supplies up to three chunks. There is no learned reranker. Responses are received as Ollama token streams but the UI displays the fully validated answer at once. It keeps six recent chat messages; document prompts do not treat earlier assistant replies as evidence. There is no microphone, ASR, TTS or voice interruption implementation.

## Evaluation method

The fixed [reference case](../evaluation/reference_case.py) uses the actual calculation methods for a 250 kg vehicle, 0.28 m wheel radius, 8:1 reduction at 0.95 efficiency, 30 N m peak torque, 4.4 kW peak power, Crr 0.018 and CdA 0.6 m². It has no uploaded motor curve, efficiency map or battery DC cap. The [oracle](../evaluation/ground_truth.json) separates numeric values, required facts, expected source and behavior when evidence is missing. The 90 questions cover 14 direct powertrain, 8 direct acceleration, 12 engineering explanation, 7 motor, 6 motor/controller, 6 cross-analysis, 21 document, 8 unavailable-data, 3 ambiguous and 5 conversation cases.

The [benchmark runner](../evaluation/benchmark_runner.py) executes the same route as the sidebar and records question, selected state, raw/selected retrieval evidence, exact model messages, raw and guarded answers, model/dataset/pipeline hashes, latency and score in per-question JSONL checkpoints. Each row is flushed and synced; `--resume` validates the existing prefix before continuing. The score checks values within stated tolerances, expected fact terms, source retrieval/citation and refusals. It is a **rule-match triage score**, not a certified accuracy percentage. We manually reviewed high-risk explanations and document statements because a cited answer can still misstate the source, and an extractive fallback can score despite being hard to read.

All latency measurements are from this machine's local Ollama installation and GTX 1650 with 4 GB VRAM. Warm-model text generation was measured; the study does not measure end-to-end speech latency. The paired comparisons use identical question IDs and request profiles within each comparison.

## Baseline and changes

The original full Qwen3 4B [baseline](../evaluation/results/baseline/qwen3_4b_full.summary.json) scored **0.585** by the rule metric over 90 questions, with **10.41 s median** and **14.84 s p90** end-to-end. It made 73 model calls. The first existing run had stopped at row 51 and the runner would have overwritten it, so checkpoint validation and resume were added before completing the baseline.

The final checkpointed [Qwen3 pipeline run](../evaluation/results/production/qwen3_4b_full_v3.jsonl) scored **0.971** on the same 90-case rule metric, with **0.0007 s median** and **5.98 s p90** end-to-end; it made 15 model calls. The model-called median was **6.53 s** and p90 **8.64 s**, so the near-zero overall median reflects local checked routes, not faster text generation. Direct powertrain and acceleration categories each scored 1.000 by the rubric. The 21 document questions scored 0.994 and selected the expected source first in 21/21; all 21 were answered through retrieval plus checked source rows or exact spreadsheet reads, with **zero chat-model calls**. This establishes good behavior on the present documents, not general RAG reasoning on unseen documents. The [side-by-side machine summary](../evaluation/results/production/comparison_final.json) keeps category and model-call details.

Changes were driven by observed failures:

- State questions now read the actual snapshot for top speed, grade, 0–60 time, launch force/torque, base RPM and selected inputs. The Acceleration snapshot includes the last plotted metrics and labels them as possibly predating input edits. The UI's “Use current analysis” switch is respected.
- Checked arithmetic and physical relationships answer narrow questions directly; ambiguous follow-ups ask which result the user means. The app guide was corrected where it implied an unimplemented manufacturer RPM cutoff.
- Document retrieval prefers explicitly named testing/product files and reranks by terms, phrases and section. A schema question now selects the chunk with `inputs` and `measurements`. Exact U546 spreadsheet facts are read from the indexed table rather than inferred by the model.
- Missing acceptance criteria, approval records and manufacturer ratings get evidence-limited answers. Citations must match supplied source IDs; unsupported numerical document limits/timings are rejected. Short checked replies use explicit local test-table rows when present.
- A compact voice request profile limits generated text and prompt size. It is benchmark infrastructure and a proposed runtime profile; the current UI still selects one chat model and does not expose a voice agent.

The [retrieval evaluation](../evaluation/results/retrieval_final_v2.json) selects the expected document first in **21/21** document questions; the baseline supplied the expected source in 12/21. This is document-level recall. Passage relevance and answer fidelity still need inspection. The initial final run exposed a missing schema-fields passage despite the correct document; the rerank now selects its `inputs`/`measurements` chunk. It also exposed hard-to-read excerpt fallbacks when the model omitted a citation, prompting the checked table-row replies.

Six final-run rows still carry automatic failure labels. Manual inspection found the certification, IP67 acceptance, product overspeed and AIS approval replies correctly say that the needed evidence is unavailable; their refusal wording misses the rubric's narrow regex. The hub-test and gear-change replies cover the intended concepts but miss one expected word. These labels remain in the raw run instead of being erased or silently rescored. A blind engineering review and a broader refusal/fact scorer are needed for a trustworthy accuracy rate.

These now have checked source-based replies. A later document answer cited a related chunk instead of the exact over-current row; the checked table response cites the row that contains the method. The rule score alone did not catch all these errors.

## Production choice

**Fast conversation / voice text model: Qwen3 4B instruct with the compact voice profile and local state-answer routes.** It beat Llama3.2 3B on rule score and had slightly better median generation latency and first-token latency in the paired local test. Local checked replies are essential for straightforward vehicle results; the model should not recompute those values. Keep voice replies to one or two sentences with a low token cap. This is a text-model selection only; direct voice-agent readiness still requires ASR/TTS, streaming playback, interruption handling and an end-to-end speech latency benchmark.

**Reasoning / engineering model: Qwen3 4B instruct with the engineering profile, RAG evidence and checked calculations.** It outscored Gemma3 4B on the hard subset and was materially faster. For numerical engineering questions, use app calculations and explicit inputs as the source of values; for document/standards questions, require the exact retrieved passage and source ID, and avoid product approval verdicts without test evidence.

These are two production **roles**, backed by the same model on this 4 GB GPU. The tests do not justify a second distinct local checkpoint as a better default. If separate serving hardware is available and two distinct checkpoints are a deployment requirement, Llama3.2 3B is the tested alternate voice candidate, with its measured quality loss and lower p90. The [single model-switch observation](../evaluation/results/models/model_switch_observation.json) saw roughly 7–9 s load time when alternating Qwen and Llama on this GPU, which defeats the fast-voice target. A separate resident voice service would need its own hardware and a fresh deployment benchmark.

## Limits and next validation gate

The current benchmark has one reference vehicle and one local document collection. It is not a holdout test across motor sizes, file formats, temperatures, user phrasings or unseen manuals. Checked replies for common rows in the present testing catalogue improve reliability there but should be tested on new documents rather than assumed to generalize. The rule score can be inflated by keyword matches and retrieved-source citations; manually grade answer correctness and citation-level support on a blinded holdout before treating it as an engineering accuracy KPI. No measured road test, controller phase-current rating, thermal-derating curve or certification decision is available from the focused app paths.

The final production-run paths and exact resume command are in [evaluation/HANDOFF.md](../evaluation/HANDOFF.md). **417 tests pass**. Resume was tested on an already complete run and on a file with an interrupted trailing JSON row; the partial row was backed up and no completed question was repeated.
