# Powertrain and Acceleration assistant architecture (inspection snapshot)

Inspection date: 2026-10-05. This is the architecture summary before optimization. Source of truth is the code and local reference files; the assistant cannot independently operate the UI or recalculate a plot.

## Application and data flow

- **Frontend:** Python `customtkinter`/Tkinter desktop window with Matplotlib plots (`main.py`, `vmi/app.py`). There is no browser frontend.
- **Backend/API:** In-process Python mixins, not a web backend. `vmi/dispatch.py` reads UI entries, calls `vmi/physics.py` for Crr/CdA, then dispatches to `vmi/torque_force.py` and the other analysis mixins. The only HTTP API in this path is the local Ollama API (`/api/chat`, `/api/embeddings`, `/api/tags`). There are no application REST endpoints or DTO layer; UI widget values and Python dictionaries serve as state objects.
- **Analysis modules:** `torque_force.py` plots powertrain torque, force and acceleration; `physics.py` estimates road coefficients; `calc_ext.py` provides battery power caps, effective mass, top-speed crossing and time integration; `parametric.py` estimates top speed, grade and acceleration for report/sweeps; `enhancements.py` reports observations. Other modules cover drive cycles, efficiency, range, engines, MTPA/MTPV, mechanical design, BOM and comparison.
- **Assistant:** `vmi/assistant.py` owns the sidebar, captures selected input fields, result observations and sampled plot lines, starts background workers, and marshals the final answer to Tk through a queue. `vmi/assistant_core.py` routes simple conversation, checked arithmetic, unsupported UI actions, state reads, document questions, and model questions. This is a routed chat workflow, not a tool-using autonomous agent. The current selectable chat model defaults to `qwen3:4b-instruct` in `vmi/llm_client.py`. There is no separate fast/engineering model selection in production yet.
- **Streaming and history:** Ollama streams HTTP JSON lines. The client records first token and generation timing, but the UI validates the full answer before displaying it, so users do not see tokens as they arrive. The sidebar retains the last six user/assistant messages in memory and logs exchanges to a local JSONL file. Prompt assembly excludes prior assistant replies for document questions. The fixed system prompt plus app guide are in `assistant_core.py`; each request adds a compact live state and at most three retrieved excerpts within a character budget. The model runs with context 4096, temperature 0.2, up to 1024 generated tokens and `think=False`; the default model is forced to GPU when possible, with fallback.

## RAG and local runtime

- `vmi/rag_store.py` indexes supported PDF, DOCX, XLSX/XLS, TXT, Markdown, CSV and JSON files under `knowledge_base/`. PDF chunks retain page metadata; spreadsheets are converted to row CSV plus peak-value facts. The available local references include an India motor-testing DOCX, an MTPA/MTPV PDF, mechanical-design Markdown, and U546 torque-speed and efficiency spreadsheets. App internals are explained through the hard-coded app guide rather than indexed as documents.
- Text is split into 300-word chunks with 50-word overlap. A file mtime/digest manifest enables incremental rebuilds and duplicate suppression. Vectors from Ollama `nomic-embed-text` (`search_document:` and `search_query:` prefixes) live in a persistent Chroma cosine collection at `knowledge_base/.index`. Query embeddings use CPU to avoid evicting the chat model from limited VRAM.
- Retrieval combines a named-product-file shortcut with the 12 nearest vector candidates, a fixed cosine-distance cutoff of 0.33, and a lexical/source heuristic rerank. Up to three hits enter the prompt. There is no learned cross-encoder reranker. The cutoff was tuned on this knowledge base and needs retesting after any embedding/index change. The guard verifies citation identifiers and blocks a few unsafe verdicts; it does not verify that a cited sentence is faithful to its source.
- Ollama is running locally and exposes installed Qwen3 4B, Gemma3 4B, Llama3.2 3B, Phi4-mini, Qwen3-VL 2B/4B, Llama3.1 8B and the Nomic embed model. The `ollama` executable is not on this shell's PATH. No llama.cpp or vLLM integration was found.

## Focused feature inventory

The full 58-entry machine-readable inventory is `evaluation/capability_map.json`. Inputs shared by the two views include reference mass, rear load ratio, wheel radius and dynamic-radius factor, gear ratio and efficiency, wheel inertia, optional Crr and CdA, gradient list and unit, peak torque and power, continuous power, peak/rated torque ratio, optional battery DC voltage/current limit, fallback battery-to-shaft efficiency, and ambient temperature/pressure for coefficient estimation. Optional motor torque-speed and motor/controller efficiency uploads alter capability. The Acceleration view adds target speed and simulation duration. Plot choices include motor/wheel part, torque/force output, speed units and axis bounds; thermal duty-point overlays and battery-map smoothing are optional controls. Shared Crr1 and altitude entries are not applied in these two views.

Powertrain outputs include calculated mass/Crr/CdA; motor RPM and theoretical base speed; peak and continuous motor torque envelopes (or uploaded curve); wheel torque and tractive force; rolling/aero/grade road load; plot force crossings; report flat-road top-speed and maximum startable-gradient estimates. Acceleration outputs include available-minus-resistive force, effective inertial mass `m + J/r²`, speed-versus-time curve, target-time, final speed, force-crossing top speed and near-settling time. The report acceleration estimate uses a separate 0.05 s step; the plotted acceleration uses 0.001 s, so their target times can differ slightly.

Important limits in these paths: no independent controller phase-current rating, manufacturer motor RPM cutoff, traction-limited launch, controller thermal-derating simulation, distance-versus-time output, or certification verdict. A battery DC current cap is not a controller phase-current limit. The top-speed estimate is a capability/road-load crossing, not a measured road test.

## Existing evaluation artifacts and initial audit

`evaluation/build_dataset.py` generates 90 questions with a numeric oracle from actual calculations (`evaluation/reference_case.py`), code-backed explanations and local-document claims. Categories include direct results, powertrain/acceleration explanations, motor/controller behavior, cross-analysis reasoning, document retrieval, missing-data handling and conversation turns. `evaluation/benchmark_runner.py` exercises production routing and records retrieved context, answer, timings and rule scores. `evaluation/retrieval_diagnostics.py` adds raw nearest-neighbor evidence. `tests/` protects engineering formulas; older assistant questionnaires/reports are under `tests/`, `tools/` and `docs/`.

The existing baseline file has only 51 of 90 Qwen3 rows and no full summary, so it cannot support a final production choice. Its runner opens output in write mode, which would erase those rows on restart. Current automatic scoring uses regex facts and loose citation checks; its aggregate is a triage signal, not a verified engineering-accuracy rate. The baseline also omits full-case coverage and a paired fast-model comparison. These are the first evaluation issues to address after this architecture snapshot.
